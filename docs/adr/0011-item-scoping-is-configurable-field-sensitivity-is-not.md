# Item scoping is configurable; field sensitivity is not

`VAULT_ALLOWLIST` was the only configuration the server read, and it gates whole vaults. There was no way to say "this vault, but not these kinds of items" — so an operator who never wants this integration touching `DATABASE` or `SSH_KEY` items had no way to express that, and category filtering had to happen client-side after the data was already fetched and returned.

We added `ITEM_CATEGORY_DENYLIST`, a comma-separated, server-wide list of item categories the middleware refuses to surface. Unset means nothing is denied, so existing deployments are unaffected.

Enforced in all three item tools, `get_item` included. Filtering only the listing tools would leave the denylist bypassable by passing a known item id directly, including an id the agent saw before the category was denied. In `get_item` the check runs before any field is classified or logged, so a denied item returns nothing and leaves no trace in the classification log. The raw item is fetched from `op` before its category is known — that is unavoidable, since the category comes back with the item — but nothing from it is returned or recorded.

**Matching is deliberately lenient, unlike the vault allowlist.** Vault ids are opaque tokens compared exactly, because a near-miss there should deny. A denylist inverts the failure direction: an entry that fails to match denies *nothing*, silently. So categories are trimmed, uppercased, and have whitespace and hyphens folded to underscores, which makes `SSH_KEY`, `SSH Key`, and `ssh-key` equivalent — `op --format json` emits the underscore form while the 1Password UI shows the spaced form, and an operator should not have to know which. Entries matching no known 1Password category are almost certainly typos that deny nothing, so the server warns about them on stderr at startup (never stdout, which carries the MCP protocol).

**We deliberately did not extend this pattern to field sensitivity.** `SAFE_TYPES` and `SAFE_PURPOSES` in `src/classify.ts` stay hardcoded. The distinction is the direction the config can fail: a category denylist can only ever narrow what is fetched, so a mistake makes the tool less useful. An env-configurable field allowlist could *widen* the security boundary, so a typo in a shell variable would silently increase what leaks. ADR-0003's argument for the field boundary is that it depends on nothing but 1Password's own attributes; making it configurable would trade that away. Config that narrows is safe to expose. Config that can widen a boundary is not.

Per-call `categories` / `excludeCategories` arguments on `list_items` and `search_items` are a complementary idea and remain unimplemented — this ADR covers only the deployment-level guardrail.

# Use the `op` CLI (desktop session locally, Service Account on servers) instead of Connect Server

The agent will eventually need to run on a server, not just locally, but this is a single consumer of 1Password data. We decided to build the middleware once against the `op` CLI, authenticated via the local desktop session for now and via a scoped `OP_SERVICE_ACCOUNT_TOKEN` when deployed to a server — the CLI's behavior and JSON output are identical either way, so no code changes are needed at migration time. We rejected standing up a 1Password Connect Server, since that's justified when multiple independent services need centrally brokered/audited access; for one agent, a service account already provides headless, scoped, non-interactive auth without that extra infrastructure.
